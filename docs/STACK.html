01สแต็กโดยสรุป

สิบเอ็ดแพ็กเกจสำหรับรันและ build บวกอีกสี่แพ็กเกจสำหรับเทสต์ ไม่มีอะไรในนี้ที่เป็นแค่การคาดเดา ทุกเวอร์ชันคือตัวที่ pin ไว้จริงใน package.json

ชั้น แพ็กเกจ เวอร์ชัน บทบาทในโปรเจกต์นี้
UI react / react-dom 19.2.6 อินเทอร์เฟซ 2D ทั้งหมด — หน้าจอ, HUD, บอร์ดเมือง, ชั้นทับตอนต่อสู้ คอมโพเนนต์เป็นแค่การเรนเดอร์ สถานะทั้งหมดอยู่ชั้นบน
Lang typescript 5.9.3 ทุกอย่างใน src เปิด strict พร้อม noUnusedLocals และ noUnusedParameters การ import ที่ไม่ได้ใช้จึงเป็น error ตอน build ไม่ใช่แค่คำเตือนจาก linter
Build vite 7.3.2 เซิร์ฟเวอร์ dev พร้อม hot reload และ build สำหรับ production เลือกแทน bundler หนัก ๆ เพราะโปรเจกต์เป็น single-page app ที่ไม่มีเซิร์ฟเวอร์
Build @vitejs/plugin-react 5.1.1 แปลง JSX และ React Fast Refresh
Ship vite-plugin-singlefile 2.3.0 รวม JS และ CSS ทั้งหมดเข้าไฟล์ index.html ไฟล์เดียว ผลลัพธ์คือไฟล์เดียว 1.8 MB ส่งอีเมลหรือวางบน GitHub Pages ได้
Style tailwindcss / @tailwindcss/vite 4.1.17 Tailwind v4 — utility เขียน inline ใน JSX ชั้น theme เก็บเฉพาะที่ utility ทำไม่ได้ คือ panel, ปุ่ม, venue tile
Style clsx + tailwind-merge 2.1.1 / 3.4.0 รวมเป็นฟังก์ชัน cn() ตัวเดียว twMerge จัดการคลาสชนกัน เพื่อให้คลาสที่ผู้เรียกส่งเข้ามาชนะค่าเริ่มต้นเสมอ
3D three ^0.186.1 โลกแผนที่ โลกสนามรบ และฉากเดินทาง โมเดลสร้างจากโค้ด ไม่มีไฟล์ mesh ติดไปกับ build
Test vitest 5.0.2 ใช้ pipeline ของ Vite ตัวเดียวกับแอป โมดูลที่ build ผ่านก็เทสต์ผ่าน ไม่ต้องจัดการ tsconfig แยก
Test jsdom 29.1.1 DOM สำหรับเฉพาะเทสต์คอมโพเนนต์ เปิดใช้รายไฟล์ โมดูลเกมล้วนจึงไม่ต้องเสียเวลา
Test @testing-library/react / @testing-library/dom 16.3.3 / 10.4.2 ติดตั้งไว้สำหรับ query และตัวช่วยเรื่อง accessibility เทสต์ปัจจุบันขับ DOM ผ่าน react-dom/client กับ act() โดยตรง ซึ่งเพียงพอสำหรับการยืนยันว่าอะไรถูกเรนเดอร์
ไม่มีอะไรอื่นใน runtime ไม่มี state library, ไม่มี router, ไม่มี UI kit, ไม่มี animation library, ไม่มีแพ็กเกจไอคอน BattleScreen 498 บรรทัดกับ BattleWorld 781 บรรทัดเขียนเอง ไม่ได้ประกอบจากเฟรมเวิร์ก นั่นคือเหตุผลที่ build ทั้งหมดยัดลงไฟล์เดียวได้ และก็เป็นเหตุผลที่ typecheck ต้องเข้มพอจะถือมันไว้ด้วยกันได้

02ขั้นตอนการ build

มี config ไฟล์เดียว สามปลั๊กอิน ไม่มีการแตกแขนงตาม environment เกมทั้งเกมส่งออกเป็นไฟล์ HTML ไฟล์เดียวที่รวมทุกอย่างไว้ข้างใน 

// vite.config.ts
export default defineConfig({
  plugins: [react(), tailwindcss(), viteSingleFile()],
  resolve: { alias: { "@": path.resolve(__dirname, "src") } },
});

แต่ละปลั๊กอินทำอะไร

Transform

react()

คอมไพล์ JSX และเชื่อม Fast Refresh การแก้คอมโพเนนต์แล้วหน้าจออัปเดตโดยไม่ทำสถานะหาย

Style

tailwindcss()

Tailwind v4 ทำงานเป็นปลั๊กอิน Vite ไม่ใช่ขั้นตอน PostCSS สแกนซอร์สแล้วปล่อยเฉพาะ utility ที่ถูกใช้จริง

Ship

viteSingleFile()

รวมทุก chunk และ stylesheet เข้า HTML นี่คือเหตุผลที่เกมที่มีทั้ง 3D อาร์ต และตรรกะ ยังเป็นไฟล์เดียวที่พกพาได้

ผลลัพธ์ของ build

ตัวชี้วัดค่าหมายเหตุ
ผลลัพธ์dist/index.htmlไฟล์เดียว ไม่มี JS, CSS หรือ asset เกาะไปด้วย
ขนาดดิบ1,815.97 kBรวม Three.js และภาพพอร์ตแทรทที่เข้ารหัส base64
บีบอัดแล้ว785.28 kBขนาดที่ส่งผ่านเครือข่ายจริง ๆ
เวลา build~1.1 sแปลง 85 โมดูล

สินทรัพย์ที่ตั้งใจไม่เก็บใน repo

ภาพพอร์ตต้นฉบับขนาด 768×1376 รวม 18 MB ถูก gitignore ไว้ สิ่งที่ runtime โหลดจริงคือ src/game/portraitData.ts ซึ่งเป็นภาพชุดเดียวกันที่ inline เป็น base64 แล้ว ทำให้ build ยังเป็นไฟล์เดียวและ repo เล็ก ไฟล์ต้นฉบับอยู่แค่บนดิสก์

ทำไมการแยกนี้สำคัญ เพราะ game/ ไม่ import อะไรจาก React กฎของเกมจึงเทสต์ได้ใน Node ล้วน ไม่ต้องมี DOM และบั๊กในสูตรต่อสู้ไม่ต้องเรนเดอร์อะไรเพื่อหาสาเหตุ ต้นทุนคือทุกการเปลี่ยนสถานะต้องส่งผ่าน App.tsx ด้วยมือ ซึ่งคือราคาที่จ่ายเพื่อยืนยันได้ว่า UI ไม่มีกฎของเกมอยู่เลย

การไหลของหนึ่งเทิร์นผ่านแต่ละชั้น

component — a click→ App.tsx — update(fn)→ game/engine — the rule→ game/store — apply, log→ three/ — the 3D reaction→ component — re-render

ไม่มีชั้นไหนข้ามเข้าไปเรียกชั้นที่ไม่ใช่เพื่อนบ้าน คอมโพเนนต์ไม่แก้สถานะเกมเอง และ engine ไม่รู้จักคิดว่ามีคอมโพเนนต์ React อยู่

04ชั้นระบบขณะรัน

สี่ระบบย่อย แต่ละอันมีหน้าที่เดียว ระบุโมดูลที่ดูแลไว้ เพื่อให้การแก้ไขมีที่ไปอย่างชัดเจน

UI อินเทอร์เฟซ 2D

การสลับหน้าจอใช้ state เป็นสตริงตัวเดียวใน App.tsx ได้แก่ start, map, battle, gameover และแต่ละหน้ามี transition key เพื่อให้ React remount แล้วเล่นแอนิเมชันเข้าใหม่ หน้าต่างซ้อนทั้งหมดผ่านคอมโพเนนต์ Modal ตัวเดียวที่มี prop stack ซึ่งคือที่มาของหน้าตากระดาษซ้อนชั้น คือแผ่นเบี่ยงสองแผ่นอยู่ข้างหลังหน้าต่าง ไม่ใช่สองกล่องโดดวาง

  • TownMenu — ช่องเมืองหกช่อง เมนูกิลด์ย่อย ช่องบันทึกเกมที่โรงแรม
  • MapScreen — แผนที่ 3D การเลือกจุด HUD การเดินทาง
  • BattleScreen — ลำดับเทิร์น การใช้สกิล ผลรวม cut-in
  • PartyMenu — สถานะ แผนผังสกิล อุปกรณ์ กระเป๋า

Rules ตรรกะเกม

เป็น object GameState ตัวเดียว แก้ที่เดิมผ่าน callback update(fn) ไม่มี reducer ไม่มี immutable ไม่มีการ diff สถานะเป็น object ธรรมดาที่ serialize ได้ นั่นคือเหตุผลที่การบันทึกเป็นแค่ JSON.stringify บรรทัดเดียว และทุกกลไกเทสต์ได้โดยไม่ต้องเรนเดอร์

  • engine.ts — Dijkstra หาเส้นทาง ลูปต่อสู้แบบ ATB การคำนวณสถานะ การสุ่มของ
  • store.ts — newGame, arriveCity, applyBattle, advanceTime, rankOf
  • time.ts — นาฬิกาตัวเดียวของทั้งเกม การเดินทาง การต่อสู้ การพักผ่อน การข้ามวัน
  • inv.ts — Record ที่ key ด้วยไอเทม จำนวนกองจึงไม่ติดลิมิตอาร์เรย์คงที่

3D โลกสามฉาก

สามฉากแยกกัน มีแค่ฉากเดียวที่ mount พร้อมกัน โมเดล เท็กซ์เจอร์ และแอนิเมชันทุกอย่างสร้างตอนรัน ตัวละครคือชุด primitive ที่ถูกจัดท่าด้วย rig เมืองคือแลนด์มาร์กที่ประกอบจากเรขาคณิต เท็กซ์เจอร์คือการวาดลง canvas นี่คือเหตุผลที่ไม่มีไฟล์อาร์ตติดไปด้วย

  • BattleWorld — 781 บรรทัด ไฟล์ที่ใหญ่ที่สุด เป็นที่รันลำดับการแสดงสกิล
  • MapWorld — ภูมิประเทศ ถนน แลนด์มาร์ก 26 เมือง แสงเปลี่ยนตามเวลา
  • TravelWorld — การเดินระหว่างสองจุด ใช้ rig ชุดเดียวกับสนามรบ

Data เนื้อหาในรูปข้อมูล

ตัวเลขสมดุล ลำดับการแสดงเอฟเฟ็กซ์ และสูตรคราฟต์ อยู่ในไฟล์ข้อมูล TypeScript ธรรมดาที่ไม่มีพฤติกรรมติดมา เพิ่มสกิลหรือสูตรคือเพิ่มหนึ่งรายการในอาร์เรย์ ไม่ใช่ไปแก้ switch

  • data/economy/ — วัตถุดิบ 12 ชนิดพร้อมตารางดรอป 15 สูตรคราฟต์
  • data/fx/ — เอฟเฟ็กซ์ 32 ตระกูล primitive 52 ตัว และ feature flags
  • game/data.ts — เมือง อาชีพ สกิล และกราฟถนนที่ generate ขึ้น

ทุกเอฟเฟ็กต์ในการต่อสู้อ่านออกเป็นโปรแกรมสั้น ๆ สกิลบอกว่า “fireball” แล้วข้อมูลจะแปลงเป็นลำดับของ primitive ทั้งหมด การปล่อย วิ่งโค้ง ระเบิด แสงวูบ รอยไหม้ แต่ละอย่างมีจังหวะของตัวเอง ชั้น 3D รู้วิธีรัน primitive และไม่รู้ว่า fireball คืออะไร

Tech — 32 names, a string union→ Recipe — steps per family→ Primitive — 52 blocks→ Feature flag — quality gates→ FxRunner — executes

อาร์กิวเมนต์เป็นตัวเลขธรรมดาหรือนิพจน์เล็ก ๆ แบบ “$T*0.5” สูตรจึงยังเป็นข้อมูล ไม่กลายเป็นฟังก์ชัน ทั้งชั้นจึงตรวจดูได้ เปรียบเทียบได้ และรีวิวเป็นตารางได้

07สถานะและการบันทึก

ไม่มี state library เกมทั้งเกมคือ object เดียว แก้ผ่าน callback แล้ว serialize ได้โดยไม่ต้องมีชั้น serialise

รูปร่างของสถานะ

g: GameState = {
  partyName, gold, fame, score,
  members: Member[],   // 4 slots, each a class with levels and HP
  day, minute,         // one clock for the whole game
  location, travel,    // current node, or an in-flight path
  visited: string[], quests: Quest[], cityQuests,
  inv: Record<...>, bag,   // item id → count, so no stack cap
  npcs: NpcParty[],    // the standings you are climbing
  log: LogEntry[], stats, settings,
}

กลไกเก็บข้อมูลสองแบบ โดยตั้งใจ

ข้อมูล ที่เก็บ เหตุผล
ตารางคะแนน localStorage ตั้งใจให้อยู่ข้าม session ตารางคะแนนที่ว่างทุกครั้งที่ปิดแท็บคงไม่มีประโยชน์
การเดินทางที่กำลังไป sessionStorage กฎคือปิดเกมแล้วหาย เซฟที่รอดการ restart ของเบราว์เซอร์จะกลายเป็นเส้นทางพัฒนาถาวรอีกเส้นหนึ่งเงียบ ๆ ส่วน sessionStorage ยังรอดจากการ refresh ดังนั้นการ reload ผิดพลาดจึงไม่ถึงกับเสีย
ทีมล่าสุด localStorage ความสะดวก ไม่ใช่ความคืบหน้า ใช้เติมค่าในหน้าจัดทีม

ทำให้เซฟปลอดภัยอย่างไร

ช่องเดียว โดยตั้งใจ

หนึ่งรอบคือ roguelite เซฟจึงหมายถึง “การเดินทางที่กำลังไป” และการเริ่มใหม่คือการกระทำที่ถูกต้อง ไม่ใช่ภาระจัดการช่องบันทึก

มีเวอร์ชัน

เซฟจากเวอร์ชันเก่าจะถูก migrate ต่อไปหรือปฏิเสธอย่างสะอาด ไม่มีทางถูกโหลดครึ่งทาง เซฟจากเวอร์ชันใหม่กว่าจะถูกปฏิเสธทั้งดุ้น

ข้อมูลเสียไม่ทำให้พัง

JSON อ่านไม่ออก ไม่มีสมาชิก หรือตำแหน่งที่ไม่มีบนแผนที่แล้ว ล้วนถูกตีความว่า “ไม่มีเซฟ” ไม่ใช่ทำให้พัง

ไม่มีการเดินทางค้างกลางทาง

ตอนเขียนจะตัดการเดินทางที่ค้างอยู่ออก การกลับมาเจอกลางช่วงจะทำให้ปาร์ตี้อยู่กลางระหว่างสองจุด โดยมีโทเคนอยู่ในตำแหน่งที่ไม่มีความหมาย

เมื่อแพ้

การพ่ายแพ้คือต้นทุน ไม่ใช่จุดจบ ปาร์ตี้ฟื้นที่ HP 1 ในเมืองที่เคยไปเยือนใกล้สุด หลังเสียทอง 30% ของกระเป๋า ค่าเสียหายคือทองบวกกับการเดินไปโรงแรม เข้าหน้าจอ game over ได้เฉพาะการยอมแพ้ด้วยใจเอง

“ใกล้ที่สุด” วัดตามกราฟถนน ไม่ใช่เส้นตรง แผนที่เป็นคาบหมู่เกาะ เมืองสองเมืองอาจดูติดกันบนจอแต่เดินกันหลายวันบนเส้นทางเดียวที่เชื่อมกัน การฟื้นที่ในเมืองที่เดินไปไม่ทันคือสิ่งตรงข้ามกับการกู้ชีพพอดี และเช็กพอยต์ที่บันทึกไว้ถูกปล่อยไว้โดยเจตนา เพื่อให้การ reload ยังได้รอบก่อนแพ้

10การตัดสินใจที่ตั้งใจ

ทางเลือกที่ดูเหมือนสิ่งที่ยังไม่ได้ทำ จนกว่าจะรู้เหตุผล แต่ละข้อมีทางเลือกที่ดูสมเหตุสมผลกว่า ซึ่งถูกปฏิเสธไป

การตัดสินใจ ทางเลือกที่ตัดออก เหตุผล
ไม่ใช้ state library Redux, Zustand, Jotai object เดียวแก้ผ่าน callback เกมทั้งเกมเป็น screen tree เดียว store จึงเพิ่มชั้นกลางโดยไม่ได้อะไร ต้นทุนคือส่งต่อค่าผ่าน App.tsx ด้วยมือ
build เป็นไฟล์เดียว Multi-page output, CDN-hosted assets เกมควรเป็นไฟล์ที่ส่งให้คนอื่นได้ HTML 785 kB เปิดจาก USB จากไฟล์แนบเมล หรือบน GitHub Pages ได้โดยไม่ตั้งค่าอะไร
เซฟเก็บใน sessionStorage localStorage กฎที่ตั้งไว้คือปิดเกมแล้วหาย localStorage จะทำให้เซฟอยู่ข้ามการ restart กลายเป็นเส้นทางพัฒนาถาวรอีกเส้นหนึ่งเงียบ ๆ ขนานกับรอบ roguelite
ไม่ใช้ router React Router สี่หน้าจอกับหน้าต่างซ้อนไม่กี่ตัว สลับด้วยสตริงเดียว router จะเพิ่มสถานะ URL ในแอปที่ไม่เคยถูกลิงก์
ตรรกะเกมไม่พึ่ง React Hooks inside game modules ทำให้กฎทั้งชุดรันบน Node ได้โดยไม่ต้องเรนเดอร์ ซึ่งคือเหตุผลที่เทสต์เร็วพอที่จะรันก่อนทุก commit
ข่าวเป็น pure function Storing each day’s paper เพราะ derive จากวัน หนังสือพิมพ์ของวันที่ 5 จึงเหมือนกันทุกครั้ง ไม่ต้องเก็บอะไร และกราฟราคากับหนังสือพิมพ์จะขัดกันไม่ได้
วัดระยะตามเส้นทางตอนฟื้นที่ Straight-line distance บนคาบหมู่เกาะสองอย่างนี้ต่างกันมาก เมืองที่ดูติดกันอาจหลายวันบนถนนเส้นเดียวที่เชื่อมไป การฟื้นที่ตรงนั้นจึงไม่ใช่การกู้ชีพ
อาร์ตสร้างด้วยโค้ด GLTF models, sprite sheets ทำให้ build เป็นไฟล์เดียวและ repo เล็ก ตัวละครคือ primitive ที่จัดท่าด้วย rig เท็กซ์เจอร์คือการวาดลง canvas ต้นทุนคือทุกสินทรัพย์ต้องสร้างกลับมาจากโค้ดได้
